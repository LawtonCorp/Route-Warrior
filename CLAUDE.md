# Working in this repository

This project was scaffolded from `LawtonCorp/ios-starter`, which distills the
tooling and the expensive lessons from building Letterama
(`LawtonCorp/WordTrace`). The rules below are not style preferences; each one
was paid for.

## Architecture

- **All app logic lives in `Sources/RouteWarriorKit/`** — a Swift package that
  imports no UI framework. `scripts/kit-purity-gate.sh` enforces this in CI.
  The payoff: the kit tests run with plain `swift test` on any Mac, no
  simulator, in seconds. Keep the app target (`App/RouteWarrior/`) a thin
  SwiftUI rendering layer over the kit.
- **The `.xcodeproj` is generated, never committed.** XcodeGen produces it from
  `project.yml`; run `./scripts/bootstrap.sh`. **Regeneration discards anything
  Xcode's UI wrote** — capabilities, build settings, file references. Change
  `project.yml`, never the project.
- **The app target needs its own tests.** A green kit suite says nothing about
  wiring. On Letterama, three shipped defects — a dead input mode, an
  `@Observable` class that never published, an inert `onChange` — were invisible
  to CI because the app target had no tests. Every feature that crosses the
  kit/app boundary gets at least one assertion in `App/RouteWarriorTests/`.

## Signing and devices

- **Never put `DEVELOPMENT_TEAM` (or any signing setting) into `project.yml`.**
  CI builds unsigned and would break. The team lives in the environment
  (`ROUTEWARRIOR_TEAM`) or in gitignored `scripts/signing.local`, and
  `scripts/device-build.sh` passes it on the `xcodebuild` command line.
- **`./scripts/device-build.sh` is the one command from clone to phone.** It
  regenerates the project, builds signed with `-allowProvisioningUpdates`, and
  installs on the connected device.
- **Pick devices by `tunnelState == "connected"`, never by `pairingState`.** A
  paired-but-absent device still reports as paired.
- **Never run `killall CoreSimulatorService`.** It unmounts the simulator
  runtime, which `actool` needs *even for device builds*, and recovery is an
  8 GB redownload.
- If the app ever gains a widget or extension that shares data with the app,
  declare the App Group entitlement **in `project.yml` for both targets** —
  set in Xcode's UI it survives only until the next regeneration, and a missing
  group fails silently (the extension reads empty defaults instead of erroring).

## Building without a local compiler

When working from an environment with no Swift toolchain (e.g. Claude Code on
the web, where `download.swift.org` is blocked by policy), **GitHub Actions is
the only compiler this project has.** In that case:

1. Run the Linux-safe gates locally first: `./scripts/kit-purity-gate.sh`.
2. Check brace balance on every edited Swift file before pushing.
3. Read the diff adversarially — most compile errors are findable by reading:
   a missing `import`, an overload that does not exist, a `String` where
   SwiftUI wants something else.
4. Fetch CI job *logs* through the GitHub MCP tool, not `curl` — the API
   redirects log downloads to a blob host that proxied environments block.
   Check-run status and PR state work fine either way.
5. Do not disable TLS verification or unset `HTTPS_PROXY` to route around a
   403; it is a policy denial, not a transient failure.

## Process

- **Branch before committing**: `git checkout main && git pull`, then
  `git checkout -b claude/<topic>`. Never commit to `main`; every change lands
  through a pull request.
- When a PR is **green and waiting on a human**, say so once, in one line, and
  stop — no polling, no scheduled check-ins, no re-posting. A **red** PR is the
  opposite: that is work now.
- Record every behaviour change in `DECISIONS.md` (create it with D-001 on the
  first entry): what was chosen, what was rejected, and why. Letterama's
  version of that file settled arguments months later.
- Swift 6 language mode with strict concurrency, from the first commit. It is
  far cheaper to start strict than to migrate later.

## Verification philosophy (worth keeping even though it is philosophy)

- A fixture generated by the code under test only proves the code agrees with
  itself. **Agreement is evidence only when the implementations can fail
  independently.** For anything correctness-critical, prefer an independent
  reference implementation or externally sourced expected values.
- A ✅ on a unit test is not a ✅ on a feature; the wiring needs its own test.
- CI can verify algorithms; it cannot verify feel, latency, frame rate, or
  battery. Say honestly which claims are machine-checked and which need a
  phone in hand.
